# Три жизни задачи

Исполняемые задачи календаря и «Приоритетов» получают 90 минут: 15 + 30 + 45.
Play/pause и обратный отсчёт находятся слева от сердечек. Сердечки не открывают окно;
❤️ — доступная жизнь, 💚 — расходуемая жизнь только у работающего таймера,
🖤 — потраченная жизнь. На паузе зелёное сердечко снова становится красным. Play сразу запускает таймер,
Pause останавливает его; раскрытия карточки, условий завершения и дополнительных
сводок нет. После каждой жизни таймер автоматически останавливается: на 15, 45 и
90 минутах суммарного фокуса. Следующая жизнь запускается только новым нажатием Play;
на паузе видна её полная длительность (30 или 45 минут), зелёного сердца нет.
Завершение сохраняет остаток бюджета, повторное открытие его не сбрасывает.
На 90 минутах таймер останавливается и появляется кнопка «Подзадачи». Только эта
кнопка открывает форму с названиями минимум двух подзадач. Досрочное разбиение недоступно.
Родитель становится контейнером навсегда: только потомки получают новые бюджеты.
Подзадачи постоянно видны под родителем, у каждой свои Play/Pause, отсчёт и жизни.
В «Приоритетах» справа от веса показано общее затраченное время, включая историю
и всех потомков. На компьютере иконка удаления появляется поверх при наведении
или фокусе, без сдвига строки; на сенсорном экране она доступна постоянно.
Все неотменённые непосредственные дети обязательны. После их выполнения родитель
завершается обычным чекбоксом, без дополнительного подтверждения. Для открытия ребёнка
сначала открывают родителя. Вложенные подзадачи работают по тем же правилам.

## Уведомления в браузере

В профиле есть «Уведомления таймера»: включение, выключение и пробное уведомление.
Разрешение браузера запрашивается только нажатием «Включить». Выбор хранится в этом
браузере; запрет и отсутствие поддержки объясняются в настройке. После серверного
подтверждения окончания каждой жизни активная вкладка показывает одно системное
уведомление с названием задачи. На первых двух жизнях оно предлагает ручной Play,
на третьей — подзадачи. Сообщение также остаётся внутри Tommma до закрытия или следующего Play.

Worker отправляет checkpoint у границы жизни, не дожидаясь очередных пяти секунд.
Ручная пауза, ошибка сети, закрытие страницы, сон и загрузка старых задач не создают
уведомлений о завершении. Опоздавший ответ после ручного продолжения также не создаёт
устаревшее уведомление. Ошибка доставки не влияет на сохранение времени и Play/Pause.

Для системного показа используется Notifications API через отдельный service worker,
с резервным `Notification` для браузеров настольных компьютеров. Клик возвращает
к Tommma и не запускает таймер. Service worker не кеширует страницы, не перехватывает
запросы и не получает серверные push-сообщения. Закрытая страница не отсчитывает время.
Баннеры зависят от разрешения сайта и системных настроек уведомлений / «Не беспокоить».
В неподдерживаемом браузере остаётся сообщение внутри приложения. Tauri не затрагивается.

## Переход существующих данных

Миграция `20260907120000_task_three_lives` только добавляет поля, индексы и таблицу.
`actual_seconds`, `session_seconds` и старые JSON-чек-листы сохраняются без изменений.
Старое сохранённое время включается в своё и общее время; новый `focus_spent_ms`
начинается с нуля у всех задач. Жизни задним числом не списываются.
Старое неподтверждённое время между `session_started_at_ms` и текущим моментом
не начисляется: исторические незакрытые таймеры отображаются на паузе.
Старые чек-листы, `done_when` и `work_summary` сохраняются в данных, но не выводятся
в интерфейсе таймера и не превращаются автоматически в исполняемые задачи.

## Учёт времени

- Play/Pause сразу меняют локальное состояние; пауза фиксирует момент клика.
  Старт, checkpoint и пауза отправляются последовательно. Ответы старых команд
  не возвращают подсветку и не возобновляют уже остановленный таймер.
  Границы интервалов фиксируются до отправки запроса, а не по приходу ответа;
  задержка сохранения не начисляется повторно. Сервер подтверждает итоговое время,
  поэтому при ошибке неподтверждённый отсчёт откатывается и таймер останавливается.
- `focus_spent_ms` — единственный накопительный расход нового бюджета (0…5 400 000).
- `TaskWorkSession` хранит начало, последний checkpoint, порядковый номер,
  подтверждённое время и конец сессии. Жизни вычисляются по порогам 900/2700/5400 секунд.
- Checkpoint ограничен концом текущей жизни: остаток интервала не переносится в
  следующую жизнь. На границе сервер закрывает сессию; её повторы не возобновляют
  отсчёт. До ответа сервера интерфейс также ограничивает время этой границей.
- Worker проверяет непрерывность выполнения каждую секунду и отправляет checkpoint примерно каждые 5 секунд.
  Задержка очередного выполнения более 2,5 секунд или расхождение часов более секунды
  помечает весь неподтверждённый интервал как неоднозначный и ставит таймер на паузу. Используется длительность
  по монотонным часам, а не количество срабатываний таймера. Сервер ограничивает
  интервал своими часами; подтверждённое время сохраняется в транзакции.
- Разрыв более 15 секунд или расхождение часов более 3 секунд завершает сессию
  без начисления неоднозначного интервала. Закрытое приложение не отправляет
  checkpoints, поэтому время закрытия не начисляется. При сбое может потеряться
  последний неподтверждённый интервал, обычно до 5 секунд; он не восстанавливается
  из времени на часах. Короткий сон, неотличимый от обычной задержки планировщика,
  ограничен этим протоколом; точные OS-события сна в браузере недоступны.
- `pagehide` пытается поставить свою сессию на паузу; sessionStorage сохраняет её id
  для повторной паузы после перезагрузки. Возобновление — только явным «Начать».
- Переключение разделов, скрытая вкладка и свёрнутое окно не вызывают паузу сами по себе.
  Если браузер полностью заморозил worker, восстановление консервативно ставит паузу.
- Сервер блокирует операции по userId (`pg_advisory_xact_lock`). Частичный уникальный
  индекс запрещает две незакрытые сессии пользователя. Повторный sequence не начисляет
  время, старый sessionId не может возобновить уже закрытую сессию.
- Всё дерево использует существующую Task с `parent_task_id`, не поле повторений.
  Своё время = сохранённая история + focusSpentMs. Общее = своё + все потомки ровно
  один раз. Удаление контейнера отменяет его потомков, сохраняя записи и время.
  Отменённые задачи остаются в корзине и в сумме предков.

## API и совместимость

Существующие auth routes, JWT/cookies, data-source и авторизация не меняются.
Новые действия требуют существующей пользовательской сессии и проверяют владельца:

- `POST /tasks/:id/focus/start` — `{ sessionId: UUID }`, один id на попытку старта.
- `POST /tasks/:id/focus/checkpoint` — `{ sessionId, sequence, elapsedMs, pause? }`.
- `POST /tasks/:id/focus/pause` — `{ sessionId? }`; указанный старый id не остановит
  более новую сессию. Пауза без id — явная команда пользователя остановить задачу.
- `POST /tasks/:id/focus/split` — `{ children: [{ id, title }] }`. Первое разбиение
  доступно только после 90 минут, минимум на две подзадачи. Стабильные id детей
  защищают от повторной отправки формы. Сохранённые условия и заметки не перезаписываются.
- `PATCH /tasks/:id` — обычный `{ completed: true }` завершает и исполняемую задачу,
  и контейнер; контейнер проверяет выполнение всех неотменённых детей.
  `doneWhen` сохраняет совместимость как необязательное поле, `confirmResult` не требуется.
  В PATCH учитываются только реально переданные поля, без defaults создания.

Legacy time fields остаются в ответе, но прямые изменения их значений отклоняются
с 422. Это намеренная граница: старый клиент не должен обходить бюджет. Перед
production rollout нужно согласованно выпустить backend и web/desktop клиент.
Старый desktop сможет читать данные, но для запуска таймера потребуется обновление.
Схема ставится до нового backend; старый backend нельзя оставлять принимающим
записи времени параллельно новому. Production-миграция/публикация в эту задачу не входят.

## Проверки

```sh
npm run check:fast
backend/node_modules/.bin/tsx --test backend/test/*.test.ts frontend/test/*.test.ts
```

Интеграционный тест требует явно указанную **отдельную локальную** БД с именем
`tommma_focus_test_*`; при другом адресе/имени он пропускается:

```sh
FOCUS_TEST_DATABASE_URL=<local-test-url> backend/node_modules/.bin/tsx --test backend/test/task-focus.test.ts
```

`backend/test/task-focus-api.test.ts` дополнительно требует `FOCUS_TEST_API_URL`
локального сервиса на этой БД и `FOCUS_TEST_JWT_SECRET` его тестового JWT-ключа.
Он проверяет разбиение после 90 минут, запуск детей без условий, завершение родителя
обычным PATCH, сохранение исторических полей и каскадную отмену.

Применить миграции в отдельную тестовую БД через `DATABASE_URL=<local-test-url>
npm --prefix backend run prisma:deploy`. Поднять проверяемый backend через
`mdev run --env MDEV_API_PORT={port} --env DATABASE_URL=<local-test-url> test -- node backend/dist/server.js`.
Полный check может использовать этот уже работающий сервис:

```sh
SMOKE_USE_RUNNING_BACKEND=1 BASE_URL=<mdev-url-test> npm run check
```

Не направлять smoke на production: он создаёт синтетического пользователя и задачи.
В smoke входят старые auth/task/priority сценарии и новый контракт из
`scripts/task-focus-smoke.mjs`. PostgreSQL-тест проверяет границы бюджета, конкуренцию,
повторы, истечение сессии, изоляцию и разбиение; frontend-тест — пороги и рекурсивную сумму.
